# AI Clinical Decision Support Lite — Discussion and Defense Report

## 0. Executive Summary

This project provides evidence-grounded clinical guideline question answering for clinicians and other clinical users working with the indexed WHO hypertension guidance.

Headline results from the saved 30-question benchmark (`benchmark_30_results.json`), using equal-weight RRF at K=3:

- **191 indexed chunks** in the benchmarked corpus.
- **60.0% primary Precision@3** across 10 reviewed primary questions.
- **100.0% paraphrase PageRecall@3** across 10 held-out paraphrase questions.
- **100.0% negative-control abstention** across 10 out-of-scope questions.

The single most important limitation is that the system has not been clinically validated beyond this small, fixed guideline corpus and benchmark, so these results do not establish safe real-world clinical deployment.

## 1. Phase 1 — Ingestion & Indexing (Day 1)

### What was done and why

The ingestion pipeline reads every PDF in `config.DATA_DIR` (`data/`) with `PyPDFLoader`, creates one page-level document per extracted page, cleans repeated guideline headers and page-number noise, attaches citation metadata, splits the pages into chunks, embeds those chunks locally, and persists them in the Chroma collection `clinical_guidelines`. This creates a searchable evidence base while preserving `document_name`, a human-readable 1-indexed `page_number`, and a stable `chunk_id` for later citations.

### Verified corpus and index counts

The current `data/` directory contains **2 PDF files** and `load_pdfs(config.DATA_DIR)` loaded **104 pages**:

| Document | Extracted pages | Indexed chunks | Pages represented by indexed chunks |
| --- | ---: | ---: | ---: |
| `Guideline for the pharmacological treatment of hypertension in adults.pdf` | 61 | 114 | 58 |
| `WHO-NMH-NVI-18.2-eng.pdf` | 43 | 77 | 42 |
| **Total** | **104** | **191** | **100** |

These figures were measured against the current files and persisted Chroma collection using the project `.venv`; the Chroma collection count is 191. The 100 represented pages is lower than the 104 loaded pages because pages that produce no usable chunk text do not receive an indexed chunk. The saved benchmark independently records the same current index size as `corpus_chunks: 191`.

### Chunking and text cleaning

`config.py` sets `CHUNK_SIZE = 500`, `CHUNK_OVERLAP = 75`, and `CHARS_PER_TOKEN = 4`. Therefore, the splitter target is approximately 2,000 characters with approximately 300 characters of overlap. `ingest.py` uses `RecursiveCharacterTextSplitter` with the separator priority `"\\n\\n"`, `"\\n"`, `". "`, `" "`, then the empty separator, which favors paragraph, line, and sentence boundaries before falling back to spaces or characters.

The cleaning function is explicitly described in `ingest.py` as:

> `"Remove repeated headers, orphan page numbers, and excess whitespace."`

The implementation removes the configured repeated WHO/guideline headers, removes lines containing only page numbers, collapses repeated spaces and tabs, and strips the result. Page metadata is applied before splitting, so the splitter preserves the source document and page metadata on the resulting chunks. Each chunk then receives an ID in the form `{document_name}_p{page_number}_c{counter}`.

### Embedding model and rationale

The active embedding model is **`BAAI/bge-small-en-v1.5`**, configured in `config.py` and constructed in `ingest.py` through `FastEmbedEmbeddings`. The code documents the operational reason for this choice: it is a local embedding model that requires no API key; the configuration also labels it “Local, no-API-key-needed.” This makes ingestion and retrieval independent of a paid or remote embedding service. Comparative quality claims belong to Phase 2 and are not inferred here.

### Day 1 documentation gaps to carry forward

The current code and files do not fully match `DAY1_REPORT.md`:

- `DAY1_REPORT.md` reports **190 chunks**; the current persisted collection contains **191**.
- Its per-document table reports **76 chunks** for `WHO-NMH-NVI-18.2-eng.pdf`; the current count is **77**. The first document remains 114 chunks.
- The report says “all the documents 7” in `data/`, but the current `data/` directory contains **2 PDF files**.
- A report example cites `WHO_Hypertension_Guideline_2021.pdf`, but that filename is not present in the current `data/` directory or the current indexed metadata; the active files are the two filenames shown in the table above.
- The report describes the index write as using `Chroma.from_documents` with IDs, while the current `ingest.py` implementation constructs `Chroma` and calls `add_documents(..., ids=[...])` in batches. The current implementation is the source of truth for the present index.

## 2. Phase 2 — Retrieval Optimization (Day 2)

### Test-set methodology

The original `evaluation_set.py` contains 10 positive questions and 2 original negative controls. The positive questions cover both active PDFs: six questions target the pharmacological hypertension guideline and four target the HEARTS technical package. Each positive item stores an expected document and reviewed source-page list. The labels are declared in the file as grounded in indexed PDF text rather than generated from retrieval output; the notes identify the clinical section or page rationale.

For the 30-question benchmark, `evaluation_set_30.py` combines:

- **10 primary positives** from `evaluation_set.py`.
- **10 held-out paraphrases** from `evaluation_set_robustness.py`, with different wording and paired ground-truth pages.
- **10 negatives**: the two original out-of-scope controls, six hard negatives from adjacent clinical domains, and two additional unrelated clinical controls.

The benchmark therefore evaluates page-level retrieval against reviewed labels, while negative controls are evaluated by whether the top dense score stays below each case's configured maximum. Negative questions are not used as positive recall labels.

The implementation retains `dense_score` separately for abstention; RRF rank scores are not used as calibrated relevance probabilities.

### Chunk-size and reranking experiments

`chunk_ablation.py` defines three intended transient tests: 300/40, the current 500/75, and 700/100 tokens/overlap, scored with Precision@5. The current run did not produce a complete ablation table or result file; it stopped around Chroma/telemetry initialization. Therefore, no ablation winner is claimed here. The current 500/75 setting remains in `config.py` because it is the active production index configuration, not because a completed current ablation has been verified in this report.

The code supports two FlashRank paths: dense-first reranking in `dense_reranker.py`, and RRF candidate fusion followed by reranking in `hybrid_retriever.py`. `benchmark_30.py --with-rerank` is opt-in. No completed reranker metrics are present in `benchmark_30_results.json`; the saved `BENCHMARK_30_REPORT.md` records that the attempted FlashRank run stalled after model initialization. FlashRank is therefore not part of the measured production recommendation.

### Final configuration and decision

There are two distinct conclusions. The **best measured offline retrieval policy** is equal-weight RRF at K=3, with the dense score preserved as the abstention signal. However, the **current runtime default** is still Dense at K=3: `config.py` sets `TOP_K = 3` and defaults `RETRIEVAL_MODE` to `dense`; RRF is available through the opt-in retrieval mode. This distinction is important: the benchmark supports RRF as the quality-leading experiment, but the checked-in default has not silently been changed to RRF.

The older `DAY2_REPORT.md` claims 63.3% current Dense Precision@3, 190 chunks, and an 8 ms latency. The fresh K run and saved 30-question benchmark instead report 56.67% Dense Precision@3 on 191 chunks; the current run's mean latency was 35.5 ms. These are documented contradictions for Section 8, not blended into a single number.

## 3. Phase 3 — Grounded Generation & Safety (Day 3+)

### Response schema

The actual schema is `schema/response_schema.json`, Draft 7. It requires these five top-level fields:

| Field | Required shape and meaning |
| --- | --- |
| `status` | String, exactly `grounded` or `abstain` |
| `answer` | String; empty for an abstain response by the prompt contract |
| `evidence` | Array of string evidence snippets |
| `citations` | Array of citation objects |
| `confidence` | String, exactly `confident`, `uncertain`, or `insufficient` |

Top-level extra properties are rejected. Each citation must contain `document_name` (string) and `page_number` (integer or string); `chunk_id` is optional in the citation schema. The schema also permits optional `reason` and `top_score` fields, plus `generation_method` (`llm`, `extractive_fallback`, or `none`) and `retrieved_chunks`. Retrieved chunks must contain `text`, `document_name`, `page_number`, and `chunk_id`, with additional metadata allowed inside those chunk objects.

The API applies the schema in `app.py`: it loads the JSON schema, creates a `jsonschema.Draft7Validator`, validates the result returned by `answer_question`, and returns HTTP 500 with schema violations instead of passing an invalid response through. `llm_client.parse_and_clean_json` parses and normalizes model JSON, but the final API-level schema enforcement is in `app.py`; the parser itself does not call `validate_clinical_response`.

### Provenance verification

There is an actual source-checking function: `llm_client.verify_response_provenance`. Its contract is:

> `"Return provenance errors for citations and evidence in a model response."`

For a grounded response, the function builds the set of retrieved `chunk_id` values and source document/page locations. It then requires at least one citation, rejects a citation whose `chunk_id` is not among the retrieved chunks, rejects a document/page citation not present in the retrieved locations, requires at least one evidence snippet, and checks that every normalized evidence snippet is contained in the normalized text of at least one retrieved chunk. It also rejects an empty grounded answer. Abstain responses intentionally bypass these grounded citation/evidence requirements.

`generation.answer_question` invokes this function after a live LLM response is parsed. Any provenance error raises an exception, so the model response cannot be returned as a successful grounded answer. The contract tests verify both sides: a matching citation/evidence pair is accepted, while a fabricated source and fabricated evidence are rejected.

### Abstention and refusal behavior

The exact code conditions are:

1. If retrieval returns no chunks, `_abstain` returns `status="abstain"`, empty answer/evidence/citations, `confidence="insufficient"`, `generation_method="none"`, and the reason `No relevant guideline evidence retrieved.`
2. Otherwise, `generation.py` takes the preserved dense score from the first result and abstains when `top_score < config.OUT_OF_SCOPE_MAX_SCORE`. The current configured threshold is **0.65**. The reason includes both the observed score and the threshold.
3. If the live LLM path is unavailable or fails, production behavior abstains when `ALLOW_EXTRACTIVE_FALLBACK` is false, with the reason `Live LLM generation is unavailable and extractive fallback is disabled.`

The code does not use a keyword blacklist as its main refusal mechanism. A reranker score is also not used as the scope signal; the dense score is deliberately retained for this guard.

### Refusal categories actually tested

The saved 30-question test construction in `evaluation_set_30.py` tests these ten negative categories: breast-cancer screening, community-acquired pneumonia/antibiotics, type 1 diabetes insulin, COVID booster guidance, appendicitis in pregnancy, pediatric asthma dosing, antidepressant choice in older adults, stage 4 chronic kidney disease/dialysis, breast-cancer chemotherapy, and acute ischemic stroke. The six hard-negative cases in `evaluation_set_robustness.py` separately cover diabetes, infectious disease, surgery, pediatric respiratory disease, psychiatry, and nephrology. `verify_day3_dod.py` directly checks a breast-cancer screening refusal, while `tests/test_contracts.py` checks abstention semantics and that abstentions need no citations.

The expanded Day 4 test data also contains additional categories such as anticoagulation, statins, heart failure, pulmonary embolism, vaccines, hypothyroidism, unrelated wellness/history/programming questions, and an explicit unsafe prompt-injection request. Those are not all part of the 30-question benchmark, so they should not be described as Day 3 refusal coverage. Prompt-injection behavior is therefore not comprehensively tested by the Day 3 unit tests or the saved 30-question benchmark.

### Live LLM integration and fallback

The live path is genuinely wired. `llm_client.call_nim_chat` sends an HTTP chat-completions request to the NVIDIA NIM endpoint, defaulting to `https://integrate.api.nvidia.com/v1/chat/completions`, with default model `meta/llama-3.1-8b-instruct`. It requires `NV_API_KEY`, supports configurable endpoint/model variables, uses a 30-second default timeout, and retries HTTP 429/5xx responses according to `LLM_MAX_ATTEMPTS` and `LLM_BACKOFF_SECONDS`.

When `NV_API_KEY` is absent, the live call is skipped. When it is present but the request, JSON parsing, schema path, or provenance check fails, `answer_question` logs the failure and falls through to the extractive fallback. That fallback selects one sentence from the retrieved chunks using token overlap with the question and returns `generation_method="extractive_fallback"` with citations and evidence excerpts. In development, `ALLOW_EXTRACTIVE_FALLBACK` defaults to enabled; in production it defaults to disabled, so unavailable or failed live generation becomes a schema-valid abstention instead of an extractive answer.

The resulting system therefore has three real output paths: grounded live LLM output, grounded extractive fallback in non-production, and abstention. The fallback is not true generative synthesis and may omit clinically important qualifiers, which is why production disables it by default.

## 6. Known Limitations and Trade-offs

### Small and narrow corpus

The active corpus is only **2 WHO hypertension PDFs**, totaling **104 extracted pages** and **191 indexed chunks**. This narrow scope makes source traceability manageable and supports a clear abstention boundary, but it also limits generalization. A strong result on this corpus does not establish performance on other diseases, institutions, guideline publishers, populations, or larger indexes. The current benchmark is correspondingly a retrieval validation exercise, not external clinical validation.

### Limited evaluation coverage

The saved benchmark contains **20 positive questions** and **10 negative controls**. Its positives cover reviewed primary questions and held-out paraphrases, while its negatives cover several adjacent medical domains. That is useful anti-overfitting evidence, but it is still a small, fixed test set. Prompt-injection, near-domain, citation, and abstention coverage is broader in the expanded Day 4 materials than in the Day 3 unit tests and 30-question benchmark, and the production checklist still requires clinician-reviewed evaluation. The failed or incomplete current-run experiments also mean that bge-base, chunk-size ablation, and FlashRank reranking do not have complete current metrics to support a decision.

### External LLM dependency

Live generation depends on the NVIDIA NIM chat-completions API, an `NV_API_KEY`, network availability, endpoint availability, model availability, and a response that can be parsed and provenance-checked. The client retries selected 429 and 5xx failures, but retries do not remove the dependency or guarantee availability. External inference also introduces operational cost, latency, and a need to manage the API credential as a secret. The production checklist explicitly requires secret management, TLS, monitoring, and clinician-reviewed safety evaluation before deployment.

### Extractive fallback is not true generation

When the live LLM is absent or fails, development mode can return a grounded response from `_select_best_sentence`: it selects one sentence from retrieved chunks using token overlap with the question. This is useful for local operation and deterministic fallback, but it is extractive rather than generative. It can omit qualifiers, combine no new synthesis, and fail to express the complete clinical context needed for a safe recommendation. Production therefore disables extractive fallback by default and abstains when live generation is unavailable.

### Retrieval-quality trade-offs

K=3 is selected because it reached 100% page recall and document hit on the current positive set while retaining more precision than larger K values. It does not make every retrieved chunk relevant: current Dense Precision@3 is 56.67% on the 10-question K evaluation and on the primary portion of the saved 30-question benchmark. Equal-weight RRF improves saved benchmark quality to 60.00% primary Precision@3 and 46.67% paraphrase Precision@3, but RRF remains opt-in at runtime and its rank score is not a calibrated probability. The system must keep using `dense_score` for the abstention guard.

### Safety boundary is score-based

The main abstention boundary is a top dense relevance score below **0.65**, not a full clinical reasoning or intent-classification system. The benchmarked negatives passed this guard, but query expansion reduced negative-control abstention to 90%, demonstrating that retrieval changes can affect safety behavior even when positive recall improves. This is a deliberate trade-off: a simple, inspectable guard is easier to audit, but it cannot by itself guarantee that every clinically unsafe or adversarial question will be rejected.

### Operational readiness is incomplete

The code includes authentication, rate limiting, request limits, security headers, health probes, schema checks, provenance checks, Docker/Gunicorn paths, and audit metadata. The project documentation still requires production infrastructure and governance work: managed Redis, TLS/reverse proxy, secret storage, centralized monitoring, clinician-reviewed testing, source provenance manifests, and disaster recovery. The current contract suite passed 15/15, but broader clinical and deployment validation remains required.

**Answer:** The active configuration uses 500 tokens, 75-token overlap, and a 4-characters-per-token approximation. The intended ablation compares 300/40, 500/75, and 700/100, but the current ablation did not complete, so a measured claim that 500/75 is globally optimal would be unjustified. **Answer:** The positive labels in `evaluation_set.py` specify expected documents and reviewed source pages, and the file states that they are grounded in indexed PDF text rather than circular retrieval output. The 30-question benchmark separates 10 primary questions, 10 differently worded held-out paraphrases, and 10 negatives. This is a reasonable anti-overfitting design for an engineering benchmark. It is still small and not an independently reviewed external clinical test set, so the honest answer is that further clinician-reviewed and externally sourced evaluation is needed.

### Refusal logic

**Question:** How does the system decide not to answer?

**Answer:** It abstains when no chunks are retrieved or when the top preserved dense score is below the configured 0.65 out-of-scope threshold. If live generation is unavailable or fails, production abstains because extractive fallback is disabled there. The 30-question benchmark achieved 100% negative-control abstention for Dense and equal-weight RRF, while query expansion reduced that result to 90%. The guard is auditable and tested, but score-based refusal alone cannot guarantee rejection of every adversarial or near-domain question.
